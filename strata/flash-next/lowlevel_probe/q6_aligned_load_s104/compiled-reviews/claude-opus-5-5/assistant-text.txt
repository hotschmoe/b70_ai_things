## Dataflow evidence from the excerpts (not just counts)

**Reconstruction, `ql` (lines 150\u2013178).**
- `and \u22124` aligns the address down to 4 bytes, then one SIMD32 `load.ugm.d32x4` fetches d0..d3 (r34, r36, r38, r40).
- The predicate `f1.0` is set from `(addr & 2) == 0`, computed on the unaligned low dword (line 166).
- `sel` picks the raw `d[i]` when that predicate holds; otherwise it picks `(d[i] >> 16) | (d[i+1] << 16)`. This matches `half ? funnel : d` exactly.
- The fifth dword is a `d32` load at the aligned address + 16 (lines 375/377). It feeds `o[3]` through `(d3 >> 16) | (d4 << 16)` (lines 382, 391\u2013393).

**Reconstruction, `qh` (lines 190\u2013201, 383, 394\u2013398).**
- Same pattern. The fifth-dword address r35 is derived from r64 at line 383, *before* r64 is reused for the scales address at line 385, so there is no stale operand.

**Bounds.** The reads span the aligned base plus 0..19 bytes. Combined with the host `base % 4` guard, this matches the source bound proof. The real-byte and guard gates still apply at runtime.

**Integer path.**
- Signed byte centering is unchanged: `bfn` plus the add/xor \u221232 sequence.
- The 48 DP4As run as ordered chains of 4, with the accumulator seeded per chain, e.g. lines 461\u2013463 and 715\u2013719.
- The signed int\u2192float conversions sit immediately before use.

**FP path, column 0.**
- Line 476: `dsc0 = d(h\u2192f) \xd7 scale` (r36).
- Line 480: `acc2 = dsc0 \xd7 ds0`. Source order is `ds0 \xd7 dsc0`; this is a commuted product, which is exact.
- Line 482: `r72 = acc2 \xd7 float(s0)`.
- Lines 682 and 685: `dsc1 \xd7 ds1`.
- Line 686: `mad r18 = r72 + r20 \xd7 float(s1)`.
- Line 687: a separate `add` into the column accumulator r78.
- Columns 1\u20135 repeat this with their own accumulators: r80, r82, r84, r88, r90.
- Reusing `acc2` across columns is safe: each use is rewritten before it is read.
- **Contraction:** one `mad` fuses the second-term product with the addition. The original has the same 6 MADs under the same flags, and the original's prefix matched public byte for byte. So this form is the inherited production form, not a new contraction. Whether the operand roles are identical to the original is settled only by the strict runtime bytes.

**K loop.** `r52 += 4` (line 390), compared against blocks per row (line 677), with a back edge to L1632.

**Reduction and stores.**
- XOR16 uses a register-indirect gather whose index is lane^16 times 4, offset by 0x1380. 0x1380 = 4992 = 78 \xd7 64, so this is r78's own GRF.
- XOR8, 4, 2 and 1 follow as mov swaps, each followed by an `add` (own + permuted).
- The stores are predicated on lane 0. Each column has its own offset (r3.0, r3.1, r1.1), one `store.d32` per column: lines 922, 963, 1003, 1046, 1086, 1130.

**Resources.**
- SIMD32 at GRF128 with eu_thread_count 8, as in the original.
- The spill, scratch and SLM fields are absent, which means unknown, not zero. No scratch-labelled sends were found.
- The extra `illegal` entry is post-EOT data.
