**S142 interpretation**

Observation: removing the profiler bundle on the same binary cut the verifier submit bracket from about 3.2 ms to under 0.1 ms and the whole window from about 57 ms to about 46 ms, while the pair poll bracket grew and the combined pair submit-to-return moved only about 0.6 ms. Inference: the S136 and S95 cycle timings, including the 3.3 ms post-pair gap and much of the 6.7 ms left region, carry a profiler-induced host-side inflation of roughly a fifth of the cycle. Treat the traced gaps as instrumentation artefacts until an unprofiled signal reproduces them. The family rankings of GPU service remain usable as relative structure, not as budgets. The practical consequence is that the real decode cycle is nearer 46 ms, and the unprofiled commit bracket of about 1.6 ms is the right readout for S144.

**One mechanism to prepare in parallel: batched GDN state and convolution commits.**

Source facts: the commit graph issues 36 layers times 2 owner groups of state-only recurrence replays plus the same count of convolution history commits, 144 launches per commit, each layer and owner fully independent in state, inputs and outputs. The recurrence kernel replays the accepted prefix in order and writes one final state; there is no stored per-row checkpoint, so selecting a last state is not available and the replay arithmetic must stay. The convolution commit is copy-only.

Mechanism: one batched launch per kind over an array of per-layer, per-owner parameter records indexed by a grid dimension, each work-group running the existing per-layer body unchanged on its own pointers and keep count. This preserves the per-cell FP ledger because no arithmetic, order or reduction changes, only which launch hosts which group. It is the same launch-count lever S141 just validated for the indexer, applied to the two largest commit launch families. Both the unprofiled commit bracket and the real cycle are the right readouts.

Source audit needed before implementation, bounded: confirm the recurrence kernel's grid and local-memory use per layer so a batched grid keeps the same work-group shape and register footprint; confirm the parameter records fit in a by-value argument or one small device array uploaded in the same graph before the commit kernels; confirm no cross-layer static scratch. Then the finite strict oracle on one card: real geometry, synthetic states for several layers and two owners, keep counts one to the window maximum, per-layer control versus batched candidate, complete state and conv history bytes, guards, read-only inputs, A, B, A, eager and captured; only then whole-commit-chain timing.
