## Stage B - full operation and data-movement census (the core of this campaign)
Goal: a complete, quantitative ledger of every GPU op and every data movement, on both cards, for these scenarios
on the Stage-A winner binary and DD config:
  B1 C1 decode steady window; B2 C2 decode; B3 cached C4 decode; B4 cold C4 (four ~20K prompts arriving together,
  prefill interleaved with decode); B5 forced RAM restore of a long (>=128K) conversation through first token;
  B6 a 32K prefill alone.
For each scenario record, per card:
  - every kernel: name, shape/quant/tile (decode kernel args or build-time names), launches per window, device
    time mean/p50/p95, share of window, bytes it must read (weights/KV/activations) -> achieved GB/s vs 608 roofline;
  - every data movement: H2D, D2H, D2D, cross-card (EP push/PSUM return/reduce, mirror), host-staged copies,
    RAM KV streaming (--kv-resident), conversation park/restore, PLE NVMe/page-cache reads: bytes, count, duration,
    engine (copy engine vs compute), and whether it is on the critical path;
  - sync points: host event waits, queue barriers, ep_wait / spin loops, fences, graph launches vs eager launches,
    host gaps between submissions (unprofiled host idle measured separately, see trace_final_analysis.md caveat);
  - host-side work per window: scheduler/admission, sampling, MTP draft/verify bookkeeping, tokenization,
    Python server overhead (py-spy or perf if available; record what was not measurable);
  - critical path per window: which chain of ops on which card bounds the window, and the idle/spin per card.
  - GPU HW metrics where obtainable (unitrace metric groups, e.g. ComputeBasic / memory BW) for the top kernels.
Also answer explicitly: (1) why per-stream decode falls 134.6 -> 65.4 -> 37.3 from C1 to C4 (what grows with rows:
attention/KV reads, expert union growth, launches, serial per-slot work, host); (2) why cold C4 prefill serializes
and what blocks interleaving; (3) where the 2.08 s forced-restore TTFT goes beyond the 211 ms native restore;
(4) what changed vs old night at C2/C4 (old trace data is in the night-lab reports; re-trace the old release
only if needed to explain a regression).
Method rules: profiled runs are diagnostic; every timing claim that matters gets an unprofiled confirmation with the
same binary. Keep raw traces under /mnt/vm_8tb/b70/results/conc-0216/ (large files fine, on disk). Write parsers into
strata/flash-next/concurrency-0216/tools/ (reuse summarize_trace.py where possible).
Deliverables: strata/flash-next/concurrency-0216/LEDGER.md (human summary tables per scenario, ranked critical-path
costs), ledger CSV/JSON per scenario under strata/flash-next/concurrency-0216/ledger/, and an updated data map
