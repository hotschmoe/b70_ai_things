# vLLM 0.26.0 NVFP4 TP=2 profile at 200K

Date: 2026-07-27

## Config

- Model: `nvidia/Qwen3.6-27B-NVFP4`
- Image: `vllm-xpu-env:int8g-v0260`
- Runtime: vLLM 0.26.0, torch 2.12.0+xpu,
  vllm-xpu-kernels 0.1.11.1
- TP=2, `MAXLEN=200000`, `UTIL=0.85`, `MAXSEQS=8`
- PIECEWISE graph, MTP5, calibrated fp8 KV, native E4M3 NVFP4
  scales for M<=8
- Prefix cache enabled
- Graph push-all-reduce enabled, `PUSH_AR_MAXB=268435456`
- `CCL_TOPO_P2P_ACCESS=0`

The profile followed the full long-context qualification, which passed an
exact 190,048-token retrieval and a 52K-token concurrent soak.

## Command

Each mode used a fresh server because repeated Kineto start/stop has been
unreliable in one XPU worker:

```bash
./bin/gpu-run bash vllm/nvfp4/profile_tp2_v0260.sh decode
./bin/gpu-run bash vllm/nvfp4/profile_tp2_v0260.sh prefill
```

The decode request generated 256 forced tokens. The prefill request used
5,210 prompt tokens and one output token. Runtime traces are under:

```text
/mnt/vm_8tb/b70/profiles/v0260_tp2_decode_vVFh6N/
/mnt/vm_8tb/b70/profiles/v0260_tp2_prefill_HN77td/
```

## Result

### Decode

Rank 1 is the representative trace:

| category | device time | share |
|---|---:|---:|
| all-reduce / collective | 491.26 ms | 41.2% |
| linear GEMM | 429.07 ms | 36.0% |
| GDN / mamba scan | 115.18 ms | 9.7% |
| attention | 75.26 ms | 6.3% |
| elementwise / copy | 49.00 ms | 4.1% |
| sampling / logits | 26.33 ms | 2.2% |

The largest individual kernel is 625
`oneccl_allreduce_pcie<bf16>` calls: 464.16 ms, or 39.0% of total
device time. These are the eager full-vocabulary MTP gathers. The graph
push kernel `do_ar` accounts for 25.98 ms, or 2.2%.

Rank 0 recorded the same kernel counts but reported the 625 oneCCL
kernels as 5.76 seconds instead of 0.46 seconds. This is profiler-induced
rank asymmetry, not a serving result: rank 1 matches the earlier v0.25.1
trace and the unprofiled server has balanced TP behavior. Do not average
the two ranks.

### Prefill

The ranks agree closely:

| category | rank 0 | rank 1 |
|---|---:|---:|
| linear GEMM | 53.1% | 52.3% |
| all-reduce / collective | 32.8% | 33.7% |
| GDN / mamba scan | 5.4% | 5.4% |
| attention | 5.1% | 5.0% |
| elementwise / copy | 1.7% | 1.6% |

On rank 1, graph push kernels consume about 673.5 ms (31.4% of total)
while oneCCL consumes only 49.3 ms (2.3%). The large prefill
collectives therefore reach the intended push transport.

## Verdict

The v0.26.0 profile reconfirms the optimization ordering:

1. Decode is communication-bound, but the 2026-07-28 validation found a
   concurrency tradeoff rather than a universal replacement. The custom
   fused shard top-1 op was token-exact and raised c4 aggregate from
   103.0 to 115.7 t/s, but cut c1 from 48.9 to 32.5. Falling back to the
   full gather at M=1 restored c1 to 48.6 but regressed c4 to 93.4 as
   active batch shapes switched. Profile the pure fused path to separate
   compact-pair collective latency from the 0.091 ms top-1 kernel.
2. Do not spend the next session replacing the NVFP4 GEMM. The existing
   decode GEMM is already at the measured B70 memory-bandwidth roofline.
3. Prefill push-all-reduce is working. Its 33-34% share is real work on
   the fast transport, not an accidental oneCCL fallback.
4. GDN is a secondary 9.7% decode target. It cannot match the potential
   gain from eliminating the 39.0% eager gather.

The env-gated local-argmax implementations remain default-off. The fused
form is useful evidence and a possible explicit throughput mode, but it
does not meet the shelf requirement of a coherent best static setting
without sacrificing interactive speed.
